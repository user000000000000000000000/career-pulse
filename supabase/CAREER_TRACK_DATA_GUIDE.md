# Данные для карьерного трека — гайд для парсера

Схема — в `supabase/schema.sql` (4 новые таблицы в конце файла: `specialties`, `profession_specialty_map`, `institutions`, `institution_programs`). Этот файл описывает, **что именно** должно лежать в каждой таблице, в каком формате и где это реалистично найти. Обновление — раз в год перед приёмной кампанией, вручную.

---

## 1. `specialties` — официальные специальности и их ЕГЭ

| Поле | Тип | Пример | Комментарий |
|---|---|---|---|
| `code` | text (PK) | `09.03.01` | Код направления по классификатору Минобрнауки (ОКСО/ФГОС) |
| `name` | text | `Информатика и вычислительная техника` | Официальное название направления |
| `level` | `bachelor` \| `specialist` \| `college` | `bachelor` | Бакалавриат / специалитет / СПО |
| `ege_required` | text[] | `{russian, math_profile}` | Предметы, нужные ВСЕГДА для этого направления |
| `ege_choose_one_of` | text[] | `{informatics, physics}` | Нужен хотя бы один предмет из списка (вуз может уточнять, какой именно принимает) |

**Список кодов предметов для `ege_required`/`ege_choose_one_of`** (держите фиксированным словарём, не текстом на русском — так проще матчить с профилем пользователя из Block1 `B1`):
```
russian, math_base, math_profile, physics, informatics, history,
biology, chemistry, english, literature, geography, social_science
```

**Где брать:**
- Основа — федеральный перечень направлений подготовки (Приказ Минобрнауки, актуальный ОКСО/ФГОС) — это стабильная часть, меняется редко
- Конкретный набор ЕГЭ формально может немного отличаться по вузам в рамках допустимого перечня для направления — если парсить по вузам слишком трудоёмко для MVP, берите **типовой набор** для кода направления (в 90%+ случаев вузы используют одинаковый или почти одинаковый набор для одного и того же кода)
- Агрегаторы с уже структурированными данными по направлению+ЕГЭ: **postupi.online**, **ucheba.ru**, **vuzopedia.ru** — у них есть карточки направлений с перечнем экзаменов

**Пример строки:**
```json
{ "code": "09.03.01", "name": "Информатика и вычислительная техника", "level": "bachelor",
  "ege_required": ["russian", "math_profile"], "ege_choose_one_of": ["informatics", "physics"] }
```

## 2. `profession_specialty_map` — какая профессия атласа к какой специальности ведёт

| Поле | Пример | Комментарий |
|---|---|---|
| `profession_id` | `11` | id из `frontend/src/data/professions.js` (напр. 11 = Data Scientist) |
| `specialty_code` | `01.03.02` | ссылка на `specialties.code` |
| `relevance` | `primary` \| `secondary` | Основной путь к профессии или один из альтернативных |

Одна профессия обычно ведёт к 1-3 специальностям (`primary` + пара `secondary`). Например, «Data Scientist» (id 11 в атласе) → `primary`: 01.03.02 (Прикладная математика и информатика), `secondary`: 09.03.01, 09.03.04.

**Как заполнять:** для каждой из 105 профессий в `professions.js` (список пришлю по запросу — сейчас в файле у каждой профессии есть `id` и `name`) нужно подобрать 1-3 подходящих кода специальности. Это единственная часть, где нужна не парсинг фактов, а экспертное сопоставление (профессия ↔ направление подготовки) — его либо делаете вы/эксперт-методолог вручную, либо это можно поручить ИИ как черновик с обязательной проверкой человеком (эту часть Я НЕ буду генерировать данные сам — рискованно для точности приёма).

## 3. `institutions` — вузы и колледжи

Одна таблица на всю страну, регион — просто колонка (`region`/`city`), не повод заводить отдельные таблицы или файлы БД под каждый регион. При сборе удобно работать по одному региону за раз (как сейчас с `institutions_spb.csv`) — но заливка всегда идёт в одну и ту же таблицу.

| Поле | Пример | Комментарий |
|---|---|---|
| `name` | `МГТУ им. Баумана` | Краткое, узнаваемое |
| `full_name` | `Московский государственный технический университет имени Н.Э. Баумана` | Официальное |
| `type` | `university` \| `college` | |
| `city` | `Москва` | Для сопоставления с городом пользователя (Block1, поле `A4`) |
| `region` | `Москва` | Для аналитики по регионам |
| `website` | `https://bmstu.ru` | Сайт вуза |
| `admissions_email` | `abitur@bmstu.ru` | Почта приёмной комиссии |
| `phone_main` | `+7 (495) ...` | Телефон вуза |
| `phone_admissions` | `+7 (495) ...` | Телефон приёмной комиссии (часто отличается от общего) |
| `vk_url`, `telegram_url`, `max_url` | url | Соцсети/каналы вуза |
| `ownership_type` | `state` \| `private` | Государственный/негосударственный |
| `subject_area` | `technical` \| `medical` \| `humanities` \| `economic` \| `creative` \| `multidisciplinary` | Предметный профиль вуза |
| `department_affiliation` | `Минобрнауки России` | Ведомственная подчинённость — **отдельная ось от subject_area** (вуз может быть техническим и одновременно относиться к Минтрансу). Словарь значений — см. `Статистика_ВПО-1_2025.xlsx` в корне репозитория: это агрегированная статистика (751 организация по РФ), не список вузов, но даёт точный перечень ведомств |
| `vpo1_category` | `Министерство науки и высшего образования Российской Федерации` | Прямая копия строки-категории из того же файла, для аудита источника |

**Где брать контакты/соцсети:** обычно на странице вуза у агрегатора (как в скрапере `scrape-postupi-spb.mjs` — там уже вытаскиваются `website`/`address`; email/телефон/VK/Telegram по той же логике, просто другие CSS-классы на той же странице).

## 4. `institution_programs` — конкретная программа в конкретном вузе

| Группа | Поля | Комментарий |
|---|---|---|
| Идентификация | `institution_id`, `specialty_code`, `program_name`, `full_name_with_level`, `level`, `duration_years` | `level` дублирует `specialties.level` для удобства выборки без join |
| Форма обучения | `form` (`full_time`\|`part_time`\|`evening`) | |
| Места и конкурс | `has_budget_places`, `budget_places_count`, `paid_places_count`, `applications_count_last_year` | `contest_ratio_last_year` **не заполняется руками** — это generated column (`заявки / бюджетные места`), считается автоматически в БД |
| Баллы | `min_score_total_last_year`, `subject1_name`+`min_score_subject1_last_year` (и subject2/subject3) | **Только сумма по всем экзаменам.** Балл «за один экзамен» (как считает postupi.online — `проходной балл / кол-во экзаменов`) в таблицу не заносим вообще — решили не пользоваться этой метрикой, чтобы не путать со суммарным баллом. **Приоритетный источник для этих полей — официальный сайт вуза** (страница приёмной комиссии/программы), не агрегаторы: там баллы обычно публикуются именно как сумма. Скрапер по postupi.online (`scrape-postupi-spb.mjs`) эти поля намеренно не заполняет. |
| Особые условия | `has_additional_tests`, `additional_tests_info`, `has_interview`, `has_medical_requirements` | ДВИ/собеседование/мед.справка |
| Целевой приём и льготы | `has_target_program`, `target_places_count`, `has_lte_places` | Квота для лиц с ОВЗ/инвалидностью |
| Стоимость | `paid_cost_rub_last_year`, `scholarship_info` | |
| Прочее | `admission_year`, `link` | |

**Где брать:** сайты приёмных комиссий вузов (страница конкретной программы — обычно там весь этот блок целиком), агрегаторы вроде postupi.online дают часть полей (места/баллы) уже на уровне списка программ вуза без захода в каждую программу отдельно — так собран текущий пилот по СПб.

## 5. Отзывы — два слоя, одна лишняя таблица не заводится

- **`institution_feedback`** (отдельная таблица) — сырые данные. Одна строка = один отзыв одного человека (`source_type`: student/parent/teacher/career_counselor/alumnus, `sentiment`, `source_platform`, `text`). Копится построчно по мере соцопроса — **не сворачивать в колонки**, иначе новый отзыв просто перезапишет предыдущий.
- **Обработанная сводка — прямо в `institutions`** (не отдельная таблица: это 1:1 с вузом, разводить незачем): `feedback_summary_student`, `feedback_summary_parent`, `feedback_summary_teacher`, `feedback_summary_career_counselor`, `feedback_summary_alumnus`, `feedback_positive_highlights[]`, `feedback_negative_highlights[]`. Это то, что показывается в интерфейсе — сводка по каждой аудитории, сгенерированная на основе всех строк `institution_feedback` по этому вузу. Перегенерируется по мере роста сырых данных; `feedback_based_on_count`/`feedback_generated_at` фиксируют, на скольких отзывах и когда основана текущая версия.

## Как это будет использоваться в приложении

Как только таблицы начнут заполняться, финальный экран после 10 блоков сможет строить цепочку:
```
рекомендованная профессия (атлас, уже есть)
  → specialty_code через profession_specialty_map
    → ЕГЭ из specialties.ege_required/ege_choose_one_of
    → институты из institution_programs (отфильтрованные по городу пользователя из Block1)
```
Я уже подготовил код с этой логикой (см. `frontend/src/services/careerTrackAPI.js`) — он корректно работает и при пустых таблицах: секция про вузы просто скажет «эта часть ещё заполняется», не ломая остальной результат.

## Приоритет для MVP
Не обязательно сразу закрывать все 105 профессий. Разумный первый шаг — 15-20 самых частых профессий (IT, аналитика, дизайн, управление — судя по популярности этих категорий) и вузы/колледжи в топ-10 городов по частоте в анкетах пользователей.
